## 0. 结论速查

那两行长这样（三语中的中文版）：

```
已缓存 12 轨 · 占用 88 KB / 256 MB
命中 0/3 次 · 预取 3 部 / 46 轨 · 上屏行一致 408/416
```

| 读数 | 单位 | 统计的到底是什么 | 归谁管 | 什么时候归零 |
|---|---|---|---|---|
| `已缓存 N 轨` | 条（每份单轨字幕算一条） | **已经在线抓到并落盘**的音轨字幕正文条数 | 宿主进程 `SubtitleCache` | 只有升级改缓存格式（`INDEX_SCHEMA` 推进）或手动「清除已缓存」才归零；**宿主重启不清** |
| `占用 X / 256 MB` | 字节（自动 KB/MB） | 上面那些正文文件的大小之和 | 同上 | 同上 |
| `命中 X/Y 次` | 次（**不是轨**） | 本进程启动以来「拿指纹去查磁盘缓存」的命中比 | 同上 | **宿主进程一重启就归零**（纯内存计数，不落盘） |
| `预取 X 部 / Y 轨` | 部、轨（轨 = ziptree 里的音频条目） | 已抓下来的**作品文件树**覆盖了几部作品、几份字幕 | 宿主进程 `ZiptreePrefetch` | 「清除预取字幕」；或超出 16 部被按最近使用淘汰掉 |
| `上屏行一致 X/Y` | 次（采样帧数） | 宿主实际显示的行，与我们自己按时间轴算出来的行对上的比例 | 宿主进程 `HostLineSync` | **宿主进程一重启就归零**（纯内存计数） |

一句话记住三件事：

1. **别按「第几行」判断持久性。** `已缓存`、`占用`、`预取` 三项都是落盘家底，宿主重启后照样在；`命中` 与 `上屏行` 是本次运行的表现，宿主一死就归零（纯内存计数）。
2. **`已缓存` 与 `预取` 是两套东西**，分别存在、分别淘汰、分别清除，**不能相加**（第 3.1 节）。
3. 这些数字全都长在**宿主进程**里，设置页一个字都读不到，只能靠一条广播要回来（第 1 节）。

## 1. 这些数字从哪来（一条跨进程广播）

缓存文件落在宿主 App 的私有目录：

```
Android/data/jp.co.eisys.dlsitesound/files/subtitle_cache/
```

设置页是**另一个 UID 的进程**，受 SELinux 与分区隔离限制，直接读不到这个目录。所以整条读数链路是「问一次、答一次」：

| 方向 | 动作 | 代码 |
|---|---|---|
| 设置页 → 宿主 | `ACTION_SUBTITLE_CACHE_STATS_REQUEST`（进页面 / 回到前台 / 清理后） | `ConfigBus#sendCacheStatsRequest` |
| 宿主 → 设置页 | `ACTION_SUBTITLE_CACHE_STATS`，一次带 9 个 extra | `ConfigBus#sendCacheStats` |
| 设置页接收 | `registerCacheStatsReceiver` → `applyCacheStats` → `renderCacheUsage` | `SettingsActivity` |

9 个 extra 与它的来源一一对应：

| extra | 取值来源 | 用在哪一行 |
|---|---|---|
| `EXTRA_CACHE_COUNT` | `SubtitleCache.count()` | 已缓存 N 轨 |
| `EXTRA_CACHE_BYTES` | `SubtitleCache.bytes()` | 占用 |
| `EXTRA_CACHE_HITS` | `SubtitleCache.hitCount()` | 命中 X |
| `EXTRA_CACHE_MISSES` | `SubtitleCache.missCount()` | 命中 /Y |
| `EXTRA_PREFETCH_WORKS` | `ZiptreePrefetch.works()` | 预取 X 部 |
| `EXTRA_PREFETCH_TRACKS` | `ZiptreePrefetch.tracks()` | 预取 /Y 轨 |
| `EXTRA_LINE_SAMPLES` | `HostLineSync.samples()` | 上屏行 /Y |
| `EXTRA_LINE_MATCHED` | `HostLineSync.matched()` | 上屏行 X |
| `EXTRA_LINE_MISMATCHED` | `HostLineSync.mismatched()` | 不上屏（只进日志） |

这条链路的三个必然结果，看到怪读数时先回想这三条：

- **宿主没在跑 ⇒ 什么都读不到**，显示「宿主未运行，暂时无法读取缓存占用」。这是**如实说读不到**，不是缓存空了（显示 0 会被误读成「缓存是空的」）。
- **曾经答过就显示旧值**：只要这一页收到过一次回执，即便宿主随后被杀，读数照旧停在最后一次回执上，不会退回「读不到」。
- **设置页不会自己猜**：所有数字都来自宿主自报，设置页只做格式化。

## 2. 逐项解释

### 2.1 `已缓存 N 轨`

**含义**：本地磁盘上**已经存有正文**的音轨字幕有几条。一条 = 一份单轨字幕 JSON（`<md5>.json`）。

**口径**（`SubtitleCache#count`，即 `entries.size()`）：

- 只统计**索引里登记过**的条目，不是「目录里有多少个 .json 文件」。索引没登记的孤儿文件不算（它们会在下次启动被清扫掉）。
- 只算**正文缓存**，**不含预取**（预取在另一套索引里，见 2.4）。
- 一条条目的身份是 `(曲目数 tc, 毫秒时长 durMs, 曲目序号 idx)` 三元组的打包值。所以「同一首曲子换了个语言版本」如果时长与序号都不同，算两条。
- 极少数情况下 N 会略大于「实际不同的音轨数」：两部作品的某条轨若「同曲目数 + 同时长 + 同序号」，就是同一个身份键，允许两条并存（`code 1024` 的作品维强约束），各自占一条。

**为什么需要显示它**：

- 这是「离线能用多少」的唯一直接证据。断网前看一眼是 12 还是 0，就知道飞行模式下有没有字幕可放。
- 也是「缓存到底有没有写进去」的判据。抓字幕主链路全绿但 N 一直是 0 ⇒ 说明写在宿主私有目录那一步失败（目录权限 / 非宿主进程初始化），不是字幕没抓到。
- 配合「占用」可以反推单轨体积（实测 60–80 KB/轨），异常膨胀时能立刻看出是畸形大文件。

**常见误读**：把它当成「这个作品有多少轨」。不是 —— 它是**攒过的所有作品**的累计条数。

---

### 2.2 `占用 X KB / 256 MB`

**含义**：已缓存正文的总字节数 / 上限。

**口径**：

- 分子 = 索引里每条 `bytes` 字段之和（`totalBytes`），**不是**扫目录算出来的。所以它不含 `_prefetch` 子目录、不含写一半的 `.tmp`。
- 单位自动换挡：`≥100 MB` 取整显示 MB，`≥1 MB` 保留一位小数，`≥1 KB` 取整显示 KB，再小显示 `B`（几十字节时会看到「占用 0 B」，那是真的不到 1 KB）。
- 分母**当前固定 256 MB**（`SubtitleCache.LIMIT_BYTES_DEF`），没有 UI 可调。代码注释按「≥1600 轨」估容量（实测单轨 60–80 KB，实际能存更多）。
- 超上限时按 `used`（最近一次命中时刻）**由旧到新逐条淘汰**，直到降回上限以下（`enforceLimitLocked`）。

**为什么需要显示它**：

- 让「什么时候会开始删我的缓存」变成可见的。看着从 12 MB 涨到 200 MB，就知道快轮到淘汰了。
- 排查「缓存莫名其妙少了」：如果占用顶到 256 MB，被淘汰是设计行为，不是 bug。
- 排查「清空后不归零」：占用由索引累加，若索引与磁盘不一致（索引里有、文件被外部删了），占用会虚高 —— 这是判断索引是否损坏的第一个信号（宿主重启读索引时会自愈）。

**两个边界，必须知道**：

1. **这个读数 ≠ 磁盘真实占用**。预取的文件不在里面（体积另算，通常 30–300 KB/部）。想知道真实占用要去系统设置看 App 存储。
2. 256 MB 是**正文**的配额，预取**不占**这个额度（第 3.1 节讲为什么这是故意的）。

---

### 2.3 `命中 0/X 次`

**含义**：本进程启动以来，「拿指纹去查磁盘缓存」这件事做了 X 次，其中命中 0 次。

**口径**（`SubtitleCache#lookup` 的两个出口）：

| 情况 | 计入 | 说明 |
|---|---|---|
| 按身份键找到条目、时间轴校验通过 | 命中 +1 | 真正把本地字幕喂给了渲染 |
| 找到了条目但时间轴对不上 | 未命中 +1 | 这份条目与本次身份不是同一轨 |
| **条目命中了、但正文文件读不出来** | **命中 +1**（随后摘条目） | 计数在判别时就加了，读文件是之后的事；这类会让命中率偏乐观，日志里会跟一行 `hit but file unreadable` |
| 身份未知（时长还没读到，`identity == 0`） | 未命中 +1 | **压根没查**也算一次未命中 —— 这类会让命中率偏低 |
| 同一身份有多部作品的候选、又认不出是谁 | 未命中 +1 | 主动放弃（宁可屏幕空白，也不放来路不明的台词） |
| 从**预取池**取到 | **不计** | 走的是 `ZiptreePrefetch.take`，不进这个计数器 |

**为什么需要显示它**：

- 这是「缓存到底有没有派上用场」的量化证据。之前只能靠翻日志猜，现在一行数字就能答。
- 命中率低且 `X` 很小（例如 `0/2`）⇒ 正常：只是这次运行里恰好没赶上离线兜底。
- 命中率低而 `X` 很大（例如 `3/180`）⇒ 说明指纹对不上，值得查（时长口径变了 / 索引被外力改坏 / 一直在拿未知身份去查）。

**三个必须知道的边界**：

1. **分母是「次数」不是「轨数」**。同一条轨离线播两次算两笔。文案里刻意写的是「次」，别看成一轨。
2. **这是本进程的数**。宿主进程重启（含被系统杀、被「重启系统界面」连带影响）就归零，而 `已缓存 N 轨` 不会 —— 出现「缓存有 12 轨、命中 0/0」是正常的，`0/0` 时这一段甚至不显示。
3. **它只衡量正文缓存**。预取命中不计入，所以离线换轨成功时可能命中数不涨（那一次是预取兜的底）。

---

### 2.4 `预取 X 部 / Y 轨`

**含义**：已经抓下来的**作品文件树**覆盖了 X 部作品、共 Y 条轨的字幕。

**口径**：

- 「部」= 预取索引里登记的作品数（`ZiptreePrefetch.works()`，上限 16 部，超了按作品目录的最近使用时间整包淘汰）。
- 「轨」= 各作品里登记的轨数之和（`ZiptreePrefetch.tracks()`）。
- 一条轨 = 作品文件树里一个 `type == "audio"` 且带 `audio.vtt` 的条目，最终对应一份 `optimized/<name>.json`。
- **这是「登记数」，不是「磁盘上确有的文件数」**：某份下载失败时索引里仍留着这条，只有真正取用时才发现文件缺失（日志 `MISS ... (file not downloaded yet)`）。所以 Y 可能虚高。
- 这一段只在 `Y > 0` 时显示；一部都没预取到时整段不出现（不显示 `预取 0 部 / 0 轨`）。

**为什么需要显示它**：

- 预取是**纯后台行为，没有任何按钮**（你不需要点「下载字幕」）。既然用户没操作过，就必须有一个地方告诉用户「它自己攒了多少」—— 否则磁盘上莫名多出几十个文件，无法解释。
- 「部」决定离线覆盖面：16 部是上限，攒满后新作品会把最久没听的整部挤掉。看到部数顶到 16 就该知道覆盖范围开始滚动了。
- 「轨」是校验预取是否完整的抓手：一部 22 轨的作品，如果只登记了 3 轨，说明解析或下载大面积失败。

**必须知道的口径差异**：这里的「轨」和第一行的「轨」**不是同一把尺子**，别相加、别对比。

- `已缓存 12 轨` 数的是**正文**条目，键是宿主播放列表的三元组；
- `预取 46 轨` 数的是**作品文件树**里的音频条目，键是毫秒时长；
- 两者数量本来就不等（实测同一部作品：宿主播放列表 `trackCount = 7`，而 ziptree 里 20 条音频、16 条带字幕 —— 含子目录、台本等）。

---

### 2.5 `上屏行一致 X/Y`

**含义**：宿主自己显示的那几句字幕，与我们按时间轴算出来「该显示的那几句」，对上了多少次。

**口径**（`HostLineSync#observe`）：

- 一次采样 = 一次抓屏。只有**两侧都有内容**（宿主屏上有行、我们算出的行里也有）才计入样本，所以 `Y` 是「可比帧数」，不是「播放秒数」。
- 判定是**交集非空即一致**：两侧文本各自做「去首尾空白 + 连续空白折叠」归一化后，只要宿主任意一行能在我们的行里找到，就算这次一致。不逐行对齐 —— 字幕常常是日文一行、译文一行，两侧行序可能不同，逐行比会造出一堆假不一致。
- 只要宿主显示了行、而我们一句都没对上，就记一次不一致。
- **只统计，不接管渲染**。这个数字目前**不改变任何显示行为**，渲染仍然完全走我们自己的时间轴。

**为什么需要显示它**：

- 它是「我们算的行对不对」的唯一客观证据。以前所有关于「换轨后字幕错位」的判断都靠人眼和日志猜，现在有一个可读的比例。
- 它是**下一步要不要改渲染策略的前置条件**：如果一致性长期很高，就没有必要把渲染权交给宿主（那会带来「换轨瞬间闪上一轨台词」的老问题）；只有确认「成串失配」时才值得动。
- 日志里还带 `streak`（当前连续失配几次）与 `persistent`（连续 ≥3 次算一段，约 0.4 秒）。**单次失配基本是采样相位差，会自己消失；成串才是真错位** —— 两者修法相反，所以不能只看总比例。

**这个指标的固有限制（不是 bug）**：

宿主那侧的行是**先过我们自己的 cue 表过滤**才收进来的，所以「宿主显示了、而我们表里根本没有」这种差异**永远不会进样本**。也就是说它衡量的是「双方都承认为本轨的行里，我们算得准不准」，不是「宿主上屏内容的覆盖率」。要测后者得另开一路不过滤的抓取。

## 3. 两个具体问题

### 3.1 「预取要和已缓存分开存储」—— 现在就是分开的，而且必须分开

**现状：两条完全独立的链路，只在物理目录上同根。**

| 维度 | 已缓存（正文） | 预取（作品文件树） |
|---|---|---|
| 类 | `data.SubtitleCache` | `hook.ZiptreePrefetch` |
| 目录 | `subtitle_cache/` | `subtitle_cache/_prefetch/`（**子目录**，同根） |
| 索引 | `index.json`（JSON，带 `schema: 4`） | `<作品号>.idx`（纯文本，`Q`/`B`/`T` 三种行，无 schema） |
| 单条内容 | 一份单轨字幕正文 `<md5>.json` | 一部作品一个目录 + 每轨一份 `<name>.json` |
| 容量口径 | 总字节 ≤ **256 MB**，超了按 `used` **逐条**淘汰 | ≤ **16 部**作品，超了按目录最近使用**整部**淘汰 |
| 匹配键 | 三元组强键 `(tc, durMs, idx)` | 毫秒时长（+ 作品键认人） |
| 读取优先级 | 第一级（强键最硬） | 第二级（强键扑空才扫） |
| 清除入口 | 「清除已缓存字幕」 | 「清除预取字幕」 |
| 受「字幕缓存」总闸控制 | 是（写与读都看这个开关） | **写：不看**（联网遇到文件树就抓）；**读：分两条路**（首个音轨 seeding 看总闸，离线换轨兜底不看） |
| 升级失效条件 | `INDEX_SCHEMA` 推进 ⇒ 整批作废 + 清扫 | 无 schema，不因升级失效 |

**为什么不能合并成一套 —— 五条理由，每条都能落到具体后果上：**

1. **配额会互相残杀**
   256 MB 是正文的预算（约 1600 轨，够用几年）。预取一部作品整棵树 30–300 KB，16 部也就 1–5 MB —— 但它**按作品整包留存**，一旦并入同一个字节池，就会出现两种坏结果：要么预取的体积把正文档位挤掉（最坏情况：预取占满 256 MB，正文一条都存不下，离线全哑），要么正文的 LRU 按轨淘汰到预取文件上，把某部作品削成「只下载了一半」，那份预取从此既不能整包复用、也判断不出完整性。

2. **淘汰粒度天然不同**
   正文按「轨」淘汰是对的 —— 每一轨独立可用；预取按「部」整包淘汰才对 —— 它的价值就在于「整部都在，随便切轨都不卡」。合并后只有一种粒度，两种语义必然有一个被牺牲。

3. **键不同，索引无法共用**
   正文要 `(tc, durMs, idx)`（宿主播放列表口径）；预取手上只有 ziptree 里的毫秒时长，**拿不到 `trackCount`**（两者口径不同，推不出来）。硬塞进一张表，就得允许「有的条目有 tc、有的没有」，命中逻辑会立刻退化成猜。

4. **清除语义不同（这条最直接）**
   用户点「清除已缓存」，要的是「把离线字幕删了，腾地方」，**不是**「以后换轨都变卡」；点「清除预取」，要的是「把那些提前抓的树删了」，**不是**「我攒了半年的离线字幕没了」。合并成一个按钮后，任何一次清理都会顺带毁掉用户没打算动的那一半 —— 这正是 `code 1030` 把它拆成两枚按钮的原因。

5. **失效条件不同**
   正文缓存的身份标签一旦口径变化（`INDEX_SCHEMA` 3→4 那次），旧条目会**整批作废**，缓存读数清零一次。预取索引是纯文本、没有版本号，不受这件事影响。合并后，一次正文格式升级会连带把预取也清空。

**这套「分开」目前的真实边界（诚实说明，别当成已经完美）**：

- 物理上预取是 `subtitle_cache/` 的**子目录**，不是兄弟目录。好处是「整个缓存目录」可以一次性打包/迁移；代价是**如果有外部工具（系统清理、文件管理器、脚本）去清空 `subtitle_cache` 整个目录，预取会一起没**。代码内部两条清理链路都只动自己那半边：`SubtitleCache.clearAll()` 只删索引引用的正文文件，`ZiptreePrefetch.clearAll()` 只删 `_prefetch` 的直接子项，都不越界。
- 「占用」那条读数**只算正文**，不含预取 ⇒ 读数小于磁盘真实占用，这是已知且有意为之（第 2.2 节）。
- 正文的孤儿清扫（`sweepOrphansLocked`）只删 `subtitle_cache/` 的**直接子文件**、且只删 `.json`，`_prefetch` 是目录、不在其列 ⇒ 不会误伤预取。

---

### 3.2 「预取单部」是不是把整部作品所有音轨的字幕都拉下来？

**是 —— 拉的是这部作品里每一条「带字幕的音频」的全部字幕，一条音轨一份。** 但有四处必须说清，否则数字会对不上。

**① 拉什么**

从作品文件树 `ziptree.json` 里逐条找：`type == "audio"` 且 `audio.vtt` 非空的条目，顺着 `audio.vtt → vtt.optimized.name` 拿到那一轨的字幕文件名，然后逐个下载到 `_prefetch/<作品号>/` 下。

- **没有字幕的轨不拉**（台本、纯音乐轨、`audio.vtt` 为空的轨直接跳过）。
- 一部作品本来就没有字幕是**正常现象**，什么都不抓，也不会报错（日志记一行「作品无字幕」）。

**② 为什么不需要你点任何按钮**

宿主只要**列文件**（进作品、下载、打开文件列表）就必须先取一次 `ziptree.json`。我们就是在这一步的响应里顺手把整棵树解析出来排队下载的。

- **必须联网**：离线时不发起（省电省流量，离线也下不下来）。
- **必须真的发出请求**：据既有真机实测，不挂代理时宿主连 `play.dl.dlsite.com` 都不会去请求（有 `download_token` 但没有实际取树）⇒ 那种情况下预取连触发机会都没有，读数自然不动。

**③ 上限（防止一部畸形的包把目录塞满）**

| 限制 | 值 | 位置 |
|---|---|---|
| 单部作品总量 | 4 MB | `MAX_BYTES_PER_WORK` |
| 单份字幕文件 | 2 MB | `MAX_FILE_BYTES` |
| 一部作品最多登记几条轨 | 256（解析时就截断） | `MAX_TRACKS_PER_WORK` |
| 最多保留几部作品 | 16 部（按最近使用整包淘汰） | `MAX_WORKS` |
| 时长匹配容差 | 250 ms（只兜浮点抖动，不做模糊匹配） | `DUR_TOLERANCE_MS` |

**④ 预取 ≠ 已缓存**

预取只是「把文件抢到本地」，**不写进正文缓存**。原因是两条链路的键不同（第 3.1 节第 3 条）。真正落成「已缓存」的时机是：你**播到那一轨**、且走了离线兜底命中 —— 那一刻才顺着正常加载路径写一次正文缓存，此后这一轨就走强键命中，不再需要扫预取池。

所以两种读数的关系是：**预取是「备用库存」，已缓存是「已经开封用过的」**。预取攒了 46 轨而只缓存了 12 轨，完全正常。

## 4. 想让这些数字动起来（自测步骤）

| 想验证 | 怎么做 | 期望 |
|---|---|---|
| 已缓存 / 占用 | **挂代理**在线播放几轨，回设置页 | 轨数与占用增长（单轨约 60–80 KB） |
| 命中 | 同上播过之后**关掉代理/进飞行模式**，重播同一轨 | `命中` 分子 +1，屏上出字幕 |
| 预取 | 联网进一部作品（进入即可，不必点下载），等几秒 | `预取 X 部` 增加；日志出现 `tracks=.. queued=..` |
| 上屏行一致 | 播一段有字幕的轨，观察至少十几秒 | `Y` 增长，`X/Y` 通常 > 95% |
| 分开清理 | 先点「清除预取字幕」，再看两行 | `预取` 归零，`已缓存` 不变；反之亦然 |

> 测字幕的前提：**必须先挂代理**，否则宿主不发字幕请求，缓存与预取都不会有数据（这是本项目长期验证过的前提，不是本模块的 bug）。

## 5. 已知口径限制（误读清单）

| 现象 | 是 bug 吗 | 真实原因 |
|---|---|---|
| 缓存有 12 轨，但 `命中 0/0` 不显示 | 否 | 本进程还没查过磁盘（`0/0` 时整段隐藏） |
| 升级后 `已缓存` 归零 | 否 | 缓存索引格式升级（`INDEX_SCHEMA` 推进）⇒ 旧条目整批作废，**属预期行为** |
| 命中率长期很低（如 `3/180`） | 未必 | `identity == 0`（时长未读到）与「歧义放弃」都计入未命中，会稀释比例 |
| `预取 46 轨` 但实际能用更少 | 否 | 计数是索引登记数，下载失败的条目不会自动摘除，取用时才发现缺文件 |
| 读数与实际磁盘占用不符 | 否 | 读数只含正文缓存，不含预取；也不含 `.tmp` 残留 |
| 宿主被杀后读数还在 | 否 | 设置页会保留最后一次回执，不退回「读不到」（避免读数闪成 0 被误读为空） |
| `上屏行一致` 永远测不出「宿主有、我们没有」的行 | 否（判据形状决定） | 宿主侧的行先过我们自己的 cue 表过滤，未收录的内容不进样本 |
| 关掉「字幕缓存」后，离线**仍**能出字幕 | 当前实现如此（已知不对称） | 预取读取只在 `onSeededTrack` 那条路看了总闸；离线换轨兜底那条路（`onTrackChanged` 里 `tryResumeFromDisk \|\| tryResumeFromPrefetch`）没看。要「一关全哑」需另改代码，不是读数问题 |

## 6. 附录

### 6.1 目录结构

```
Android/data/jp.co.eisys.dlsitesound/files/subtitle_cache/
├── index.json                     ← 正文缓存索引（schema 4，原子写）
├── <md5-1>.json                   ← 单轨字幕正文（与在线抓到的字节一致）
├── <md5-2>.json
└── _prefetch/                     ← 预取（另一套索引，不占 256 MB）
    ├── RJ01728000.idx             ← Q/B/T 三行的纯文本索引
    ├── RJ01728000/
    │   ├── <name-a>.json
    │   └── <name-b>.json
    └── RJ01735000.idx …
```

### 6.2 `index.json` 条目字段

| 字段 | 含义 | 用途 |
|---|---|---|
| `identity` | 身份强键 `(tc, durMs, idx)` 打包值；0 = 时长未补盖 ⇒ 孤儿，永不命中 | 读取主键 |
| `selection` | 选择键 `(tc, idx)` | **只用于补盖时长**，不参与读取 |
| `workKey` | 作品键（URL 末段 `optimized`） | 同一身份多候选时认人 |
| `tc` / `idx` / `durMs` | 曲目数 / 曲目序号 / 时长毫秒 | 取证与日志 |
| `cues` | 解析出的字幕条数 | 日志 |
| `bytes` | 该文件字节数 | 占用合计 + 淘汰 |
| `hash` | 正文 MD5 | 同作品去重 |
| `maxEnd` | 字幕最大结束时间（秒） | 补盖时长时的时间轴交叉校验 |
| `file` | 单轨文件名 | 读写定位 |
| `created` / `used` | 写入时刻 / 最近命中时刻 | LRU 淘汰依据 |
