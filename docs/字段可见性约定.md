## 0. 为什么要写这一页

`data/SubtitleRepository` 是本模块**唯一的状态容器**：56 个实例字段、48 个 public 成员、
27 个 `synchronized (lock)` 区块（覆盖约 527 行，占全文 2,166 行的 ~24%）。

也就是说：**全文只有四分之一的行处于锁的保护范围内，而近四分之三的可变状态在锁外被读写。**

这不等于有 bug。它等于**"哪个字段该用什么纪律"没有成文**——
下一个改代码的人只能靠猜，而猜错的代价正是本项目最贵的那一类 bug
（铁律 #1「消费时读到的状态 ≠ 事件那一刻的状态」就出生在这个类里）。

这一页的目的只有一个：**把隐含契约写成明文**，让「猜」变成「查」。

### 1.1 从不进入任何锁区块的 14 个字段（硬结论）

这类字段的**唯一**可见性来源是 `volatile` 或「单写者 + 主线程读」，与 `lock` 无关：

| 簇 | 字段 | 声明复合体 |
| --- | --- | --- |
| **磁盘缓存暂存** | `stagedCacheJson`(L392) `stagedCacheWorkKey`(L394) `stagedCacheCues`(L396) `stagedCacheMaxEnd`(L398) `stagedCacheToken`(L400) `stagedCacheSelection`(L406) | `volatile` |
| **缓存可用性** | `localCacheAvailable`(L408) `lastCacheableJson`(L440) | `volatile` |
| **播放态** | `lastPlaybackState`(L449) `playingState`(L1846) | `volatile int` |
| **基础设施** | `observers`(L469) `mainHandler`(L470) `timeFormat`(L471) `cacheIo`(L479) | `final` |

### 1.2 锁内锁外都出现的 41 个字段（真问题所在）

包括**音轨裁决簇**与**身份归属簇**的全部成员：

```
裸字段 20 个：appContext / appClassLoader / cues / currentSubtitles / subtitlesVisible /
             floatingWindowOpen / playerPageVisible / pendingTrackDecision /
             pendingBaselineLoadMs / pendingToken / autoClosedForNoSubtitle /
             pendingStartPosMs / pendingSawPositionReset / pendingPosSamples /
             pendingIndexVerified / previousTrackCuesHidden / pendingSoftSuspend /
             autoClosedForPlaybackEnded / currentCueIndex / lastScannedSecond

volatile 21 个：lastLoadJsonMs / softNoSubtitles / lastNoSubtitleVerdictMs /
             observedPlaylistIdentity / cuesOwnerIdentity / observedPlaylistSelection /
             cuesOwnerSelection / cuesLoadedAheadOfIdentity / playlistRebuiltAtMs /
             cuesArrivedDuringRebuild / cuesLoadedAtMs / cuesWorkKey / lastSeenWorkKey /
             workChangeKey / workChangeAtMs / pendingTrackIdentity / pendingTrackSelection /
             lastSeenWorkKeyAtMs / playbackPositionMs / lastFedMs / subtitleLineSet
```

**同一个字段，有时在锁内读、有时在锁外读** —— 41 个字段都是这样。
`pendingToken`（换轨判定令牌）尤其值得注意：它是铁律 #76「被令牌躲过去 ≠ 已修复」的主角，
却同时存在锁内与锁外两条访问路径。

### 1.3 两个"纪律相反"的簇并排住在一个类里

这是本轮最值得记住的一条结构性事实：

| 簇 | 字段数 | 可见性手段 | 是否加锁 |
| --- | --- | --- | --- |
| **音轨裁决** `pending*` | 6 | 部分 `volatile` + 部分裸 | ✅ 有（`lock`） |
| **磁盘缓存暂存** `stagedCache*` | 6 | 全部 `volatile` | ❌ **完全不加锁** |

两簇都在处理"跨线程传递一份数据"的同一件事，却用了**相反的并发模型**。
`stagedCache*` 那套（volatile + 令牌 `stagedCacheToken`）实际是**无锁发布协议**；
`pending*` 那套是**互斥锁 + 令牌**。两套都对，但**住在一起就会互相误读**。

## 2. 约定（**成文规则，写下来就不是猜了**）

### 2.1 三组字段的定义与纪律

| 组 | 判据 | 数量 | 纪律 |
| --- | --- | --- | --- |
| **A 组 · 锁守护** | 显式进入 `synchronized (lock)` | — | 任何写都必须持锁；读也应持锁 |
| **B 组 · volatile 发布** | 有 `volatile`、**从不**进锁 | **8**（缓存簇） | **单写者**写、任意线程读；**禁止**多写者无锁 |
| **C 组 · 主线程专有** | 无 `volatile`、无锁 | **20**（裸字段） | **只允许主线程访问**；跨线程必须改为 B 或 A |
| **D 组 · 不可变基础设施** | `final` | 6 | 构造后不可变，无约束 |

### 2.2 ⚠️ C 组的隐含契约必须被遵守

C 组的 20 个裸字段**目前靠"只有主线程碰它"活着**。这条契约现在没有写在任何地方，
所以它随时可能被一次"顺手在 hook 线程里读一下"破坏。

**新增 C 组字段时，必须在本页登记并写明访问线程。**
**任何 hook 线程 / IO 线程要访问 C 组字段 ⇒ 必须先升级为 B 组（`volatile`）或 A 组（加锁）。**

### 2.3 哪些是已知的合规例外（**不要动**）

| 字段 | 为什么不加锁也不加 `volatile` |
| --- | --- |
| `appContext` / `appClassLoader` | 仅在 `init()` 里写一次，之后只读；读点都在主线程与 hook 初始化路径 |
| `currentCueIndex` / `lastScannedSecond` | 播放位置消费的**主线程专有**缓存，故意不跨线程 |
| `timeFormat` | `SimpleDateFormat` **非线程安全** ⇒ 只允许单线程用，加锁反而是错的方向 |
| `cacheIo` | `ExecutorService` 本身线程安全，只需"构造后发布"（`final` 已保证） |
| `observers` / `mainHandler` | 访问点自带 `synchronized (observers)` 或 `post`，无需外层锁 |

## 5. 统计口径

| 指标 | 口径 |
| --- | --- |
| 实例字段 | 类体内 `private` 开头、不含 `static`、形如 `<类型> <名字> (= ...)?;`；**允许初始化式跨行 / 含括号** |
| 锁区块 | `synchronized (lock)` 起始行按 `{}` 深度配平出的行区间，共 27 个 |
| 「锁内出现」 | 该字段名作为标识符出现在任一锁区块的行内 |
| 「锁外出现」 | 该字段名作为标识符出现在任一**非**锁区块的可执行行内（跳过纯注释行） |
| 判定 | 两者皆真 → `内外都有`；仅前者 → `仅锁内`；仅后者 → `仅锁外` |
| ⚠️ 已知局限 | 这是**文本级**判定，不区分「读」与「写」，也不做数据流分析。它足以支撑"纪律是否一致"的结论，**不足以**判定某处是否存在竞态 |

⚠️ **本页数字若与下轮不一致，先比这张口径表再下结论**（铁律 #42）。
